# API

REST sobre JSON bajo `/api`. No hay especificación OpenAPI: este documento es el inventario, **verificado contra los routers** (`apps/api/src/routes/`, montados en `apps/api/src/app.ts`) y contra la matriz de `http.security.test.ts`, que falla si aparece una ruta no-GET sin registrar. Para el detalle de cada módulo (reglas, ejemplos, decisiones) ver el documento enlazado en cada sección. Los esquemas exactos de entrada y salida son los de `packages/core` (Zod).

## Convenciones generales

| Tema               | Regla                                                                                                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Autenticación      | Cookie de sesión `HttpOnly` (`academic_planner_session`; bajo HTTPS, `__Host-academic_planner_session`). «Sesión: sí» = responde 401 sin ella                           |
| Dueño              | Siempre sale de la sesión. Los cuerpos son `strictObject`: un `userId` o cualquier campo desconocido da 400. El login es la única excepción, a propósito                |
| Formato            | Cuerpos y respuestas JSON (`Content-Type: application/json`); solo la importación de horario usa `multipart/form-data`                                                  |
| Fechas e instantes | Instantes en ISO 8601 UTC (`2026-10-07T15:00:00.000Z`); días de calendario como `YYYY-MM-DD`; horas de pared `HH:mm` (24 h) en la zona del perfil. La interfaz localiza |
| Caché              | Toda respuesta de `/api` lleva `Cache-Control: no-store`                                                                                                                |
| CSRF               | Las rutas no-GET exigen un `Origin`/`Sec-Fetch-Site` permitido (`INVALID_ORIGIN`, 403)                                                                                  |
| Cuerpo             | Máximo 100 kB de JSON (413 si se excede)                                                                                                                                |

### Errores

Misma envoltura siempre: `{ "error": { "code": "…", "message": "…", "details"?: … } }` (`details.fields` en validación). La interfaz nunca recibe pilas, SQL ni rutas.

| Estado | Cuándo                                                      | Códigos                                                                                                                     |
| -----: | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
|    400 | Validación, o regla que necesita datos guardados            | `VALIDATION_ERROR`, `NO_CURRENT_PERIOD`, `INVALID_JSON`, `BAD_REQUEST`                                                      |
|    401 | Sin sesión válida, o credenciales incorrectas               | `UNAUTHENTICATED`, `INVALID_CREDENTIALS`                                                                                    |
|    403 | Origen no permitido (CSRF)                                  | `INVALID_ORIGIN`                                                                                                            |
|    404 | Recurso inexistente **o de otro usuario** (misma respuesta) | `NOT_FOUND`                                                                                                                 |
|    409 | Conflicto de dominio                                        | `EMAIL_ALREADY_EXISTS`, `SUBJECT_ALREADY_EXISTS`, `SUBJECT_NOT_EMPTY`, `PERIOD_NOT_EMPTY`, `ACTIVITY_COMPLETED`, `CONFLICT` |
|    413 | Cuerpo o archivo demasiado grande                           | `PAYLOAD_TOO_LARGE` (JSON > 100 kB), `FILE_TOO_LARGE`, `IMAGE_TOO_LARGE`, `TOO_MANY_PAGES`                                  |
|    415 | Tipo de contenido o de archivo no admitido                  | `UNSUPPORTED_MEDIA_TYPE`, `UNSUPPORTED_FILE`                                                                                |
|    429 | Límite de frecuencia, o ya hay una importación en curso     | `RATE_LIMITED` (con `Retry-After`), `IMPORT_IN_PROGRESS`                                                                    |
|    504 | La extracción de un horario superó el tiempo máximo         | `IMPORT_TIMEOUT`                                                                                                            |
|    503 | `GET /api/health` cuando la base de datos no responde       | —                                                                                                                           |

## Salud

| Método y ruta     | Sesión | Para qué                                               | Respuesta                                                                                                 |

## Perfil (`/api/profile`) — [decisión D26](decisions.md#d26-perfil-educativo-separado-del-usuario)

| Método y ruta        | Sesión | Para qué                                  | Entrada                                                                               | Éxito                                                                        | Errores importantes                                                                                                                         |
| -------------------- | :----: | ----------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/profile`   |   sí   | El perfil educativo del usuario de sesión | —                                                                                     | `200 { profile: { primaryUse, programName, programKey, onboardingStatus } }` | 401                                                                                                                                         |
| `PATCH /api/profile` |   sí   | Actualizar parcialmente ese perfil        | `{ primaryUse?, programKey?, programName?, onboardingStatus? }` (estricto, ≥ 1 campo) | `200 { profile }`                                                            | 400 validación (campo desconocido, `programKey` fuera del catálogo, nombre ≠ canónico, > 80, NUL), 409 `INVALID_ONBOARDING_TRANSITION`, 401 |

**Obsoleto como autoridad (P0.5-5, [D35](decisions.md#d35-studytrack-como-autoridad-de-la-formación-y-finalización-del-onboarding-p05-5)).** Con **≥ 1 estudio**, cambiar `programName` o `programKey` responde `409 PROGRAM_MANAGED_BY_STUDY` («Tu programa se administra desde Mis estudios.») y no muta el perfil; sin estudios sigue permitido (preparación del onboarding y cuentas anteriores). Los campos se siguen devolviendo tal como están guardados y **no** se mantienen sincronizados con el estudio. Sin id en la URL: el dueño sale solo de la sesión (nunca `userId`, correo ni zona horaria en el cuerpo). Un programa del catálogo (`programKey`) trae su nombre canónico (el servidor lo deriva); un `programName` solo es un programa propio (sin clave); ambos `null` lo borran. `onboardingStatus` pide `IN_PROGRESS`, `COMPLETED` o `SKIPPED` (nunca `NOT_STARTED`) y debe ser un paso válido (`NOT_STARTED → IN_PROGRESS | SKIPPED`, `IN_PROGRESS → COMPLETED | SKIPPED`, `SKIPPED | COMPLETED → IN_PROGRESS`; pedir el estado actual es inocuo). `register`, `login` y `me` **no** incluyen el perfil. El perfil es obligatorio por invariante y la petición **nunca lo crea ni lo repara**: si un usuario autenticado no lo tuviera, `GET` y `PATCH` responden `500 PROFILE_INVARIANT_BROKEN` (mensaje genérico, error registrado en el servidor) y no escriben nada.

## Finalizar el onboarding (`POST /api/onboarding/complete`) — [D35](decisions.md#d35-studytrack-como-autoridad-de-la-formación-y-finalización-del-onboarding-p05-5)

| Método y ruta                   | Sesión | Para qué                                                                                                | Entrada (estricta) | Éxito                                                 | Errores importantes                                 |
| ------------------------------- | :----: | ------------------------------------------------------------------------------------------------------- | ------------------ | ----------------------------------------------------- | --------------------------------------------------- |
| `POST /api/onboarding/complete` |   sí   | Termina el asistente; para quien estudia, crea el estudio principal y **adopta** el periodo que ya creó | **vacía** (`{}`)   | `200 { profile, studyTrack \| null, period \| null }` | 400 (cualquier campo), 401, `409 NO_CURRENT_PERIOD` |

El servidor lo deriva todo (ni `userId`, uso, programa, ids, tipo o nombre del cliente). **Idempotente**: con el perfil ya `COMPLETED` devuelve el estado actual sin escribir. Con **algún** estudio previo no crea otro ni cambia el principal. Docente, uso personal y perfil sin respuesta: `studyTrack: null` (este último no pasa a `COMPLETED`). `period` es `null` solo para una cuenta ya terminada que hoy no tiene periodo HOME. Transaccional: un fallo no deja un estudio sin `COMPLETED` ni lo contrario.

## Estudios (`/api/study-tracks`) — [decisión D31](decisions.md#d31-studytrack-una-formación-que-el-usuario-cursa-p05-1)

| Método y ruta                             | Sesión | Para qué                                                                         | Entrada (estricta)                       | Éxito                                  |
| ----------------------------------------- | :----: | -------------------------------------------------------------------------------- | ---------------------------------------- | -------------------------------------- |
| `GET /api/study-tracks`                   |   sí   | Todos los estudios del usuario (principal, activos, archivados)                  | —                                        | `200 { studyTracks }`                  |
| `POST /api/study-tracks`                  |   sí   | Crear un estudio (el primero activo queda como principal)                        | `{ name?, type, programKey? }`           | `201 { studyTrack }`                   |
| `PATCH /api/study-tracks/:id`             |   sí   | Cambiar nombre, tipo o clave (≥ 1 campo)                                         | `{ name?, type?, programKey? }`          | `200 { studyTrack }`                   |
| `POST /api/study-tracks/:id/make-primary` |   sí   | Mover el principal (transaccional; no uno archivado)                             | sin cuerpo                               | `200 { studyTracks }`                  |
| `POST /api/study-tracks/:id/archive`      |   sí   | Archivar (no el principal si hay otros activos)                                  | sin cuerpo                               | `200 { studyTracks }`                  |
| `POST /api/study-tracks/:id/restore`      |   sí   | Volver a `ACTIVE` (principal solo si no hay otro activo)                         | sin cuerpo                               | `200 { studyTracks }`                  |
| `POST /api/study-tracks/setup`            |   sí   | Un estudio + su primer periodo (actual) + materias, **todo o nada**              | `{ track, period, subjects? }`           | `201 { studyTrack, period, subjects }` |
| `POST /api/study-tracks/adopt-period`     |   sí   | Un estudio nuevo que **adopta** un periodo existente sin estudio (no copia nada) | `{ periodId, name \| programKey, type }` | `201 { studyTrack, period }`           |

**Mis estudios (P0.5-4, [D34](decisions.md#d34-mis-estudios-y-adopción-explícita-p05-4)).** `setup` y `adopt-period` son **transaccionales** (el mismo candado por usuario que las demás escrituras de estudios) y **estrictos en cada nivel**: el cliente nunca envía dueño, `isPrimary`, estado, `periodId` del periodo nuevo, `studyTrackId`, contexto ni colores. `setup`: el primer estudio activo queda como principal, el periodo es el actual de su ámbito y las materias reutilizan las reglas del lote rápido (máx. 30, sin duplicados, tipo del estudio); un fallo deshace todo. `adopt-period`: el periodo debe ser del usuario (ajeno o inexistente: el mismo `404`) y no tener estudio (`409 PERIOD_ALREADY_IN_STUDY`); conserva su id y todo lo que cuelga de él; `409 PRIMARY_STUDY_HAS_NO_CURRENT_PERIOD` si dejaría la app sin HOME. `GET /api/subjects` sigue aceptando `?periodId=` (también el de un estudio secundario) **o** `?scope=current`, nunca ambos. La API no cambió en esta corrección: el nivel de un periodo (`studyLevel` número **o** `studyLevelNote`) ya era válido para cualquier tipo de estudio, y `GET /api/periods` (la lista que la web usa para abrir `?period=`) no depende de HOME.

No hay `DELETE`. El dueño sale solo de la sesión; un estudio ajeno, inexistente o con un id mal formado da el mismo `404`. Nunca se acepta `userId`, `id`, `isPrimary`, `status`, `periodId` ni `primaryUse`. Errores propios: `409 PRIMARY_TRACK_REQUIRES_REPLACEMENT`, `409 STUDY_TRACK_ARCHIVED`. Un periodo puede pertenecer a un estudio ([D32](decisions.md#d32-un-periodo-puede-pertenecer-a-un-estudio-p05-2)); archivar un estudio apaga sus periodos actuales y restaurarlo no los reactiva.

## Notas (sesión: sí) — [D36](decisions.md#d36-modelo-de-calificaciones-por-periodo-cortes-y-evaluaciones)

Base de B1: sin pantallas. Cuerpos `strict`; el dueño y el periodo salen de la **sesión** y del servidor, nunca del cliente; un recurso ajeno o inexistente responde el mismo 404. Notas en milésimas (`scoreMilli`), pesos en puntos básicos (`finalShareBp`, `periodShareBp`).

| Método y ruta                               | Qué hace                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/periods/:id/grading`             | Crea la escala del periodo (`minMilli`, `maxMilli`, `passMilli`, `decimals`). 201. 409 `PERIOD_NOT_TRACKED` (periodo sin estudio), `GRADING_EXISTS`                                                                                                                                                                                         |
| `GET /api/periods/:id/grading`              | `{ profile \| null, gradingPeriods[] }` (lectura)                                                                                                                                                                                                                                                                                           |
| `PATCH /api/periods/:id/grading`            | Cambia pasar/decimales; mín/máx solo mientras no haya notas (409 `GRADING_SCALE_LOCKED`)                                                                                                                                                                                                                                                    |
| `POST /api/periods/:id/grading-periods`     | Crea un corte (`name`, `finalShareBp`); la suma ≤ 100 % (400); exige la escala (409 `GRADING_NOT_CONFIGURED`)                                                                                                                                                                                                                               |
| `PATCH /api/grading-periods/:id` · `DELETE` | Edita un corte · lo borra (409 `GRADING_PERIOD_NOT_EMPTY` si tiene evaluaciones). 204                                                                                                                                                                                                                                                       |
| `POST /api/evaluations`                     | Crea una evaluación (`subjectId`, `gradingPeriodId`, `name`, `periodShareBp`, `activityId?`, `scoreMilli?`, `rawEarnedMilli?`/`rawMaxMilli?`). Con la escala empezando en 0, `18/20` sin `scoreMilli` se convierte (y en un PATCH **recalcula** la nota, nunca conserva la vieja); en otra escala el par exige `scoreMilli` explícito (400) |
| `PATCH /api/evaluations/:id` · `DELETE`     | Edita (la materia no cambia) · borra. `scoreMilli: null` limpia nota y par crudo. 204                                                                                                                                                                                                                                                       |
| `GET /api/subjects/:id/grades`              | Escala, cortes, evaluaciones de la materia y `summary` exacto (`complete`, pesos evaluado/restante/indefinido, `currentMilli`, `currentPasses`, `required`: `SECURED` \| `IMPOSSIBLE` \| `NEEDED` + `requiredMilli`); `profile: null` y `summary: null` sin escala                                                                          |

Además: `PATCH /api/activities/:id` responde 409 `ACTIVITY_LINKED_TO_EVALUATION` al cambiar de materia una actividad vinculada, y `DELETE /api/subjects/:id` 409 `SUBJECT_HAS_EVALUATIONS`.
